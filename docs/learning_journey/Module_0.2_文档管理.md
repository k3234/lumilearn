### 步骤 1：文档体系设计原则

在开始编写之前，先确立文档组织的核心原则：

| 原则 | 说明 | 反例 |
|------|------|------|
| **就近原则** | 文档与代码放在一起，而非集中堆放 | 所有文档堆在 `/docs/` 一个目录 |
| **分层原则** | README（入口）→ 模块文档（详解）→ API 文档（参考） | 一个 README 写 5000 行 |
| **时效原则** | 文档标注日期和状态，过时文档及时归档或标记 | 半年前的文档仍在首页 |
| **可发现原则** | 使用目录索引、标签、链接让文档易于检索 | 文档靠记忆找 |

### 步骤 2：Markdown 编写最佳实践

#### 2.1 标题层级规范

```markdown
# 一级标题 — 整个文档的标题（一个文档只有一个）
## 二级标题 — 主要章节
### 三级标题 — 子章节
#### 四级标题 — 细节分组（尽量不用）
```

**原则**：
- 一个 `.md` 文件只有一个 `#` 一级标题
- 标题层级严格递进，不跳级（不出现 `##` 后直接 `####`）
- 标题内容用中文，简洁明了

#### 2.2 代码块规范

```markdown
# ✅ 正确：指定语言，获得语法高亮
```python
def hello():
    print("Hello")
```

# ❌ 错误：不指定语言
```
def hello():
    print("Hello")
```
```

**语言标识参考**：

| 语言 | 标识符 | 语言 | 标识符 |
|------|--------|------|--------|
| Python | `python` | JSON | `json` |
| Bash/Shell | `bash` | YAML | `yaml` |
| Markdown | `markdown` | 纯文本 | `text` |

#### 2.3 表格规范

```markdown
| 列1 | 列2 | 列3 |
|-----|-----|-----|
| 数据 | 数据 | 数据 |

# 对齐方式
| 左对齐 | 居中 | 右对齐 |
|:-------|:----:|-------:|
| 内容   | 内容 | 内容   |
```

**表格适用场景**：
- ✅ 对比（方案 A vs 方案 B）
- ✅ 参数列表（参数名 / 类型 / 说明）
- ✅ API 端点列表
- ❌ 长文本段落（表格不适合放很长的文字）

#### 2.4 强调和引用

```markdown
**加粗** — 用于关键术语和重要信息
*斜体* — 用于轻量强调
`行内代码` — 用于变量名、函数名、命令

> 引用块 — 用于引用外部内容、总结金句、重要提示
>
> 多行引用需要在每行前加上 >

---

水平分割线 — 用于章节之间的视觉分隔
```

### 步骤 3：项目文档分级规范

LumiLearn 采用三级文档体系：

```
┌─────────────────────────────────────────┐
│            Level 1: README              │
│   项目概述、快速开始、核心功能列表        │
│   目标读者: 所有人（首次接触项目的人）     │
├─────────────────────────────────────────┤
│          Level 2: 模块文档              │
│   每个模块的详细设计、实现步骤、FAQ       │
│   目标读者: 开发者、贡献者               │
├─────────────────────────────────────────┤
│         Level 3: API / 代码注释         │
│   函数签名、参数说明、返回值、使用示例    │
│   目标读者: 调用者、API 使用者           │
└─────────────────────────────────────────┘
```

**各级文档要求**：

| 级别 | 长度期望 | 必须包含 | 可有可无 |
|------|---------|---------|---------|
| Level 1 | 200-500 行 | 简介、安装、快速开始、目录索引 | 架构图、FAQ |
| Level 2 | 100-400 行 | 目标、步骤、代码、总结 | FAQ、资源链接 |
| Level 3 | 内嵌代码中 | 参数说明、返回值、异常 | 使用示例 |

### 步骤 4：学习笔记管理方法

#### 4.1 笔记模板设计

LumiLearn 学习笔记使用统一模板（见 `template.md`），保证了：
- **一致性**：所有笔记结构相同，快速定位信息
- **完整性**：模板提示不遗漏重要内容
- **可检索**：固定的章节标题可用 `grep` 批量搜索

#### 4.2 模块编号体系

```
Module_主编号.子编号_标题.md

例：
Module_0.1_存储管理.md      ← 基础运维模块，第 1 个子模块
Module_0.2_文档管理.md      ← 基础运维模块，第 2 个子模块
Module_1.1_数据管道.md      ← 数据处理模块，第 1 个子模块
```

**编号规则**：
- 主编号：大的技术领域（0=基础运维, 1=数据处理, 2=模型训练...）
- 子编号：该领域内的具体模块，从 1 开始
- 标题：简短中文，用下划线连接

#### 4.3 笔记书写流程

```
1. 复制 template.md
     ↓
2. 填写元信息（日期、状态、难度）
     ↓
3. 明确学习目标（5-6 条可验证的目标）
     ↓
4. 编写实现步骤（分步详解，配合代码）
     ↓
5. 提取学习要点（核心知识点，独立成章）
     ↓
6. 补充 FAQ（常见踩坑记录）
     ↓
7. 添加资源链接（外部参考）
     ↓
8. 写总结（一段话 + 金句）
```

#### 4.4 README 索引维护

每次新增笔记后，更新 `docs/learning_journey/README.md` 中的索引表格：

```markdown
| 模块编号 | 标题 | 日期 | 状态 |
|---------|------|------|------|
| 0.1 | 存储管理与清理 | 2026-06-01 | ✅ 完成 |
| 0.2 | 文档管理与学习笔记体系 | 2026-06-01 | ✅ 完成 |
```

### 文档生成器核心函数

以下是一个简化版的文档模板引擎，用于自动生成学习笔记骨架：

```python
from datetime import datetime
from pathlib import Path

def 生成笔记骨架(模块编号: str, 标题: str, 难度: str = "⭐⭐☆☆☆") -> str:
    """
    基于 template.md 生成新笔记的骨架内容。

    参数:
        模块编号: 如 "0.2"
        标题: 如 "文档管理"
        难度: 星级评分，默认 2 星

    返回:
        生成的 Markdown 文本
    """
    日期 = datetime.now().strftime("%Y-%m-%d")

    内容 = f"""# Module {模块编号} — {标题}

**日期**: {日期}
**状态**: 🟡 进行中
**相关模块**: Module {模块编号.split('.')[0]}（基础模块）
**难度**: {难度}

---

## 📚 学习目标

完成本模块后，你将能够：

1.
2.
3.
4.
5.

---

## 🧭 实现步骤（分步详解）

### 步骤 1：

---

## 💻 关键代码（带注释）

---

## 🎓 学习要点（核心知识点）

---

## ❓ 常见问题（FAQ）

---

## 🔗 相关资源链接

---

## 📝 总结
"""
    return 内容


def 保存笔记(输出目录: str, 模块编号: str, 标题: str) -> Path:
    """保存生成的学习笔记到指定目录"""
    输出路径 = Path(输出目录)
    输出路径.mkdir(parents=True, exist_ok=True)

    文件名 = 输出路径 / f"Module_{模块编号}_{标题}.md"
    内容 = 生成笔记骨架(模块编号, 标题)

    with open(文件名, "w", encoding="utf-8") as f:
        f.write(内容)

    print(f"✅ 笔记已生成: {文件名}")
    return 文件名
```

## 🎓 学习要点（核心知识点）

### 1. Markdown 设计哲学 — 可读性优先

Markdown 的核心理念是**源码即文档**：即使不渲染成 HTML，纯文本的 `.md` 文件也应该是可读的。

```markdown
源码可读性测试：
# 标题              ← 明确标识
- 列表项            ← 清晰结构
**强调**            ← 可见标记

对比：
<h1>标题</h1>       ← 源码不可读
<li>列表项</li>     ← 需要解析器
<strong>强调</strong> ← 标记噪音大
```

- Markdown 由 John Gruber 于 2004 年创建
- 设计目标：用纯文本实现"出版级"排版
- 没有统一标准，存在多种方言（CommonMark、GFM 等）

### 2. 常用 Markdown 扩展语法（GFM）

GitHub Flavored Markdown (GFM) 是目前最广泛使用的 Markdown 方言，增加了以下实用特性：

```markdown
- [x] 已完成的任务        # 任务列表（勾选框）
- [ ] 未完成的任务

| 表格 | 支持 |
|------|------|             # 表格支持

~~删除线~~                  # 删除线

https://example.com        # 自动链接

```python
# 围栏代码块 + 语言标识     # 语法高亮

脚注引用[^1]               # 脚注
[^1]: 脚注内容
```

### 3. 文档即代码（Docs as Code）

将文档纳入版本管理，享受与代码同等的待遇：

| 操作 | 代码 | 文档（传统） | 文档（Docs as Code） |
|------|------|-------------|---------------------|
| 版本历史 | `git log` | 手动记录日期 | `git log` ✅ |
| 变更对比 | `git diff` | 肉眼对比 | `git diff` ✅ |
| 协作审查 | Pull Request | 邮件/聊天 | Pull Request ✅ |
| 回滚 | `git revert` | 手动恢复 | `git revert` ✅ |
| 自动化检查 | CI/Lint | 人工检查 | CI/Lint ✅ |

### 4. 常见 Markdown Lint 规则

使用 `markdownlint` 可以自动检查文档质量：

| 规则 | 说明 | 示例 |
|------|------|------|
| MD001 | 标题层级递增 | `##` 后不能用 `####` |
| MD009 | 行尾无多余空格 | `文本  ` → `文本` |
| MD012 | 无连续空行 | 最多一个空行 |
| MD022 | 标题前后有空行 | `## 标题\n\n文本` |
| MD031 | 代码块前后有空行 | 代码块与文字分隔 |
| MD032 | 列表前后有空行 | 列表与段落分隔 |
| MD040 | 代码块指定语言 | \`\`\`python 而非 \`\`\` |
| MD047 | 文件以换行结束 | 最后一行后有 `\n` |

## ❓ 常见问题（FAQ）

### Q1: 什么时候用 Markdown，什么时候用其他格式（如 Word/Google Docs）？

**A**: 取决于场景：

| 场景 | 推荐格式 | 原因 |
|------|----------|------|
| 技术文档/README | **Markdown** | 代码友好，版本可控 |
| 对外正式报告 | PDF/Word | 排版更精确 |
| 团队协作编辑 | Google Docs/Notion | 实时协作 |
| API 文档 | Markdown + 工具 | 可自动生成 |
| 学习笔记 | **Markdown** | 轻量、可搜索、Git 管理 |

### Q2: Markdown 中如何插入图片？

**A**: 推荐两种方式：

```markdown
# 方式 1：引用本地图片
![描述文字](./images/架构图.png)

# 方式 2：引用在线图片
![描述文字](https://example.com/图片.png)
```

**最佳实践**：
- 项目文档的图片放在 `docs/images/` 目录，使用相对路径引用
- 图片文件不要太大（<500KB），用 PNG/SVG 格式
- 使用有意义的描述文字（无障碍访问需要）

### Q3: 如何让 Markdown 文档支持折叠区域？

**A**: 使用 HTML 的 `<details>` 标签（GFM 支持）：

```markdown
<details>
<summary>点击展开查看详细代码</summary>

```python
# 这里放大量代码
def 长函数():
    ...
```

</details>
```

**适用场景**：
- 折叠冗长的代码示例
- 折叠可选的详细说明
- 折叠历史记录或变更日志

### Q4: 学习笔记应该写多详细？

**A**: 遵循"黄金原则"：

> 写得详细到**半年后的自己**能看懂，但不需要详细到**完全没背景的人**能看懂。

假设读者：
- 了解项目的基本背景
- 有一定的编程基础
- 但**不记得**具体实现细节

### Q5: 多个项目间的文档如何保持一致性？

**A**: 三个层次的复用：

1. **模板复用**：将 `template.md` 复制到各项目
2. **规则复用**：使用 `.markdownlint.json` 统一 Lint 规则
3. **工具复用**：共享文档生成脚本（类似 `auto_logger.py`）

### Q6: 如何处理过时的文档？

**A**: 推荐流程：

```
1. 标记过时 → 在文档顶部添加 ⚠️ 警告
      # ⚠️ 本文档已过时，最新版本请参考 xxx

2. 归档 → 移到 `docs/archive/` 目录
3. 重写 → 新建文档替代，旧文档保留作为历史参考
4. 删除 → 只有在确认完全无用时才删除
```
